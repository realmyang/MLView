## (a) Executive summary

1. **MLView is a precision instrument with a fidelity problem, not an accuracy problem.** Across four realistic projects the auditors wrote from scratch it produced **0 false positives** and **0 issues on both clean corpora** — and found **8 of ~27 planted defects (recall ≈ 26%)**, with only **5 of 20 rules** ever firing outside `samples/vision_pipeline`.
2. **Weakness 1 — the analyzer cannot see inside a class.** `core/build.py:234-238` returns early on `call.class_ir`, which `ir/scopes.py:418` sets to the *enclosing* class for every call in a method body. The flagship demo's Model lane therefore contains **no layers at all**; a Lightning `DataModule` contributes **0 op nodes**; the tool reports *"not detected: preprocess"* on files that call `StandardScaler().fit_transform`.
3. **Weakness 2 — the first screen does not deliver the one-screen promise.** `layout.ts:156` sets every lane to the widest lane's width, so a 360-node project renders a **5672×2706** world that `fit()` opens at **20%** (15% at 1280×800, the `MIN_ZOOM` floor). On the 45-node demo, `fit()` and `0` are **verified no-ops** and **9 of 15 findings** sit below the fold with nothing saying so.
4. **Weakness 3 — the tool cannot tell "I checked and it is fine" from "I could not check."** MLV101 is silent whenever features arrive as a function parameter; single-file analysis loses **57%** of a file's findings silently; a leaky notebook returns *0 issues, exit 4*; an odd-syntax file drops an entire training step with `dynamic=0` on every node. A silent miss and a clean bill of health are currently indistinguishable.
5. **The engineering debt is entirely in process, not in code.** Zero `TODO`/`FIXME` across five source trees; 10 unreferenced definitions of 513. But there is **no `.git`, no `.github`**, and `tools/verify.py --all` is **RED in the tree as delivered** — 1 of 9 — because gate 8's pytest run writes 7 `__pycache__` dirs under `claude-plugin/vendor` and gate 9 correctly refuses them.
6. **The viewer is not the bottleneck.** 400 nodes mount in **102 ms**, 1000 in **243 ms**, zero console errors. The analyzer takes **8.8 s** on a realistic 525-file repo. Every optimization hour this round belongs in Python.
7. **Recommended next sprint (Sprint 3):** unblock the gates (HEALTH-01 → CI-01), take the three byte-identical perf wins (PERF-01/02), ship eight render-only S items in parallel, stand up ANA-12's labelled corpus, then run **one controlled re-baseline release** carrying ANA-1/2/3 with the first-paint geometry fix.
8. **The one strategic bet to start now is ANA-1** — the class-method blind spot. One change simultaneously fixes the demo, the issue-anchoring bug, the honesty bug and every host, with a measured prototype showing **zero new findings on both clean corpora**.
9. **The bet to fund after that is interprocedural dataflow (DATAFLOW-IP)** — the largest recall lever on the board and the one most likely to cost the 100% precision that is the product's whole credibility. It does not start before ANA-12 exists.
10. **A named workstream nobody proposed, which both judges converged on: "never look clean when you were blind."** MLV-P2a, H6 and ANA-5a are three instances of one defect. Fund them as one workstream with a shared diagnostics vocabulary and one coverage chip in every host.

#### ★ ANA-1 · Stop swallowing every op written inside a class method

#### ANA-2 · Resolve calls made through an attribute-held callable

*quality · value 5 · **S** · risk low · depends on nothing · **rides the ANA-1 re-baseline***

**Problem.** Best value-to-effort ratio on the board. `ir/resolve.py:158-198` (`_canonical_for_receiver`) treats `self.loss_fn(logits, labels)` as *a method named `loss_fn` on `self`*, and because `self` is an `nn.Module` it proposes `torch.nn.Module.loss_fn`, which prefix-matches to role **LAYER**. Byte-identical logic, opposite outcomes. And the correct answer is **already sitting in the IR**: `binding_of("self.loss_fn", call.scope)` returns a `ValueRef(tags=MODEL,LOSS)` whose `producer.fqn` is `torch.nn.CrossEntropyLoss`. **Proposal.** When the callee is `<recv>.<attr>` and `binding_of("<recv>.<attr>", scope)` yields a `ValueRef` with a producer FQN, prepend `"<producer fqn>.__call__"` (falling back to the bare producer FQN) to the candidate list, ahead of the family-base guesses. Also tighten `_is_torch_module` so *"self is an nn.Module"* does not license fabricating `torch.nn.Module.<arbitrary attr>` when a binding for that attribute exists. Fixing a resolver that invents an FQN it was never given is a correctness fix, not a feature. One class of change to watch: self-held sklearn estimators gaining estimator receivers could newly fire MLV101/MLV102 — desirable, but it needs a clean-corpus file to pin it.

**Acceptance.** A fixture `MLV401_self_attr_bad.py` fires MLV401 at confidence ≥ 0.7; the HF project emits MLV401 high at its softmax site; the `CallSite` dump for that file shows `torch.nn.CrossEntropyLoss.__call__` rather than `torch.nn.Module.loss_fn`; the precision corpus and both samples are unchanged. #### CI-ADOPT · `--changed-since` attribution, baseline ratchet, SARIF, action, pre-commit

*new-feature · value 5 · **M** · risk: needs one amendment · depends on nothing · **merges H1 + H2 + MLV-P5***

Make MLView adoptable on a repo that already has findings. The evidence is decisive: a git-init'd copy of the sample with **7 added lines** produces **15 findings, 0 on the changed lines**, from a command (`/mlview-issues`) whose own front-matter advertises it *"for agent loops and PR descriptions"*; `grep -rniE '(git|diff|pull request|pre-commit)'` over both hosts returns no functional hit; and a realistic 50-file repo starts at **111 findings**, so `--fail-on high` exits 2 forever and the only way to adopt MLView on an existing codebase today is never to gate on it.

**Proposal, one product in four parts.** (a) Analyze the **whole** project — fidelity is the point, see COVERAGE — and attribute afterwards: `--changed-since <rev>` and `--changed-paths <file>` (the second so CI runners that already have the diff do not re-shell git), classifying each issue as `new` (loc inside an added hunk), `touched` (changed file, outside the hunks) or `existing`, emitted as an additive `Issue.change`, with `--changed-only` dropping `existing` from output and from `--fail-on` accounting. An issue whose primary loc is `existing` but which has a `relatedLoc` inside an added hunk is `touched`, **never dropped** — that is how a leak introduced upstream of an untouched fit site still surfaces. Renamed files need `git diff -M` or they read as all-new. (b) Baseline as the ratchet: `mlview baseline write`, `--baseline FILE`, matching on `(code, symbol, snippetHash)` and **reporting unmatched entries** so a stale baseline is visible rather than silently permissive; a baselined issue is marked, not deleted, so the existing "show suppressed" affordance carries it. (c) `--sarif` — a mechanical transform of `issues[]`: `rules[]` from the registry, `helpUri` from the existing `Issue.docs`, `partialFingerprints` from `Issue.id`, `uriBaseId: "%SRCROOT%"` so no absolute path escapes (GitHub rejects them). (d) A composite `tools/action/action.yml` and a `.pre-commit-hooks.yaml` with `pass_filenames: false`, because per-file invocation is exactly the fidelity bug COVERAGE describes.

**Cheaper than either audit proposed.** Both assumed ids churn on edit and wanted to invent a parallel stable identity; §0 defines `issueId = sha1(code|file|qualname|symbol)` and `test_id_stability.py` asserts ids survive a 20-blank-line insertion — **the stable identity already exists and is gated**, which drops the baseline from M to S. **Requires one amendment** lifting A6's *"baseline — do NOT build"*; that is a lead decision, and the recommendation is to grant it, because it is the measured blocker to adoption on any existing repo. Every failure path must degrade to *"unattributed, showing everything"* with a diagnostic — never to an error and never to an empty list — when git is absent, the workspace is not a repo, or the base ref does not exist.

**Acceptance.** On the PR fixture, `--changed-since HEAD --changed-only` returns 0 findings and exit 0 while the plain run still returns 15; introducing an `optimizer.step()` before `loss.backward()` inside the hunk returns exactly that one MLV203; a non-git directory returns all 15 plus a config-warning diagnostic and exit 0; the SARIF validates against the 2.1.0 schema with 15 distinct fingerprints, no absolute path, and a resolving `helpUri` for all 20 rules; re-running after 20 inserted blank lines leaves every fingerprint unchanged; `mlview baseline write` then `mlview issues .` reports 0 unsuppressed and 111 baselined, and planting one new MLV201 makes it exit 2 with exactly that finding.

#### CACHE · Content-addressed per-file cache shared by CLI, extension and MCP

`analyzeOnSave` defaults **true** and `extension.ts:395-404` re-runs a **cold full workspace analysis** 400 ms after every save, spawning a fresh interpreter with no cache of any kind: **~5.5 s of pure redundant re-parsing** per Ctrl+S on a 445-file repo, of which only 0.106 s is interpreter start. **Landed 2026-09-09 (Sprint 4 wave 3) — measurement note.** `mlview.core.cache` now owns the single content-keyed `file_signature` — `claude-plugin/server/mlview_workspace.py` is a wrapper around it and the old mtime+size key is gone — with `ingest/parse.py`'s `parse_all`, dead code until now, as the seam the proposal named. **Landed 2026-09-10 (Sprint 5 wave 1) — the default flip.** The cache ships **on**, as a consequence rather than as a second decision: §11.28 B7 keeps `--relevance all` from ever consulting the sidecar, so flipping PERF-03's default turns this one on. Normative in `docs/CONTRACTS.md` §11.39. #### ★ DATAFLOW-IP · Interprocedural value summaries

**The bet.** Recall is ~26% and the boundary is precisely the **object boundary**, which is where all real ML code lives. Two audits independently pinned it with probe ladders — a nine-variant and a four-variant one — reaching the same conclusion: MLV101 fires for an in-scope producer, for an annotated parameter and across one hop into a plain function, and is **silent** for `ctor param → self.features → read in a sibling method`. #### MLV-P12 · Multi-pipeline workspaces

*new-feature · value 3 · **L** · risk: extends a normative frozen enum · depends on HEALTH-02, VIEW-01, PERF-03*

The observation is correct: a research repo with 10 training scripts renders as one 320-node graph at 22% zoom, the analyzer **knows** there are 10 entrypoints (it lists 5 and elides the rest), and no existing selector expresses *"the exp03 pipeline"* — which is the unit a practitioner actually thinks in. Treating it as another projection rather than a new mode is exactly right: compute weakly-connected components over `data` and `call` edges seeded from `workspace.entrypoints`, emit a `pipelines[]` block, add `pipeline:<entrypoint>` to the selector grammar, and open the report on a chooser when a workspace has two or more. **But** it extends §11.1's normative `KIND` enum, and per §11.16 both `project()` implementations, `contracts/scope.cases.json`, the MCP `mlview_graph` docstring and `api`'s `SCOPE_KINDS` all move together. Additive enum extension is a legitimate amendment — just not before HEALTH-02's fuzzer can prove the port followed. Its payoff also overlaps heavily with VIEW-01 (legible large graphs), PERF-03 (relevance) and the existing `file:` and `unit:` scoping, and component detection is a judgement call that a shared `config.py` or `data/` module breaks: seed from entrypoints and mark a node reachable from several entrypoints as `viewRole: context` — the three-role vocabulary already exists — rather than forcing it into one pipeline. Revisit after the first-paint work lands and we can see whether the pain survives.

**Landed 2026-09-10 (Sprint 5 wave 3) — measurement note.** `analyzer/src/mlview/core/pipelines.py` + `webview/src/scope/pipelines.ts`, normative in `docs/CONTRACTS.md` §11.47. #### H8 · PostToolUse hook

*new-feature · value 3 · **S** · risk: noise and latency · depends on CACHE*

`claude-plugin/hooks/` and `agents/` do not exist — the plugin is entirely pull-based, so when Claude edits a training file during a session nothing tells it the edit introduced MLV203; the user finds out on the next manual `/mlview-issues`. The pieces are cheap and present: the signature cache makes an unchanged re-run **0.00 s** and the sample 0.07 s. **The discipline is the feature.** A `PostToolUse` matcher on `Edit|Write|NotebookEdit` whose script exits 0 immediately unless the edited path is Python and under `CLAUDE_PROJECT_DIR`; runs through the same `load_graph` cache the MCP tools read (sharing `MLVIEW_DATA_DIR`, so the hook *warms* the cache the tools then read for free); diffs the issue-id set against the previous run; and **emits only when the set grew**, as a bounded `additionalContext` of at most 5 rows, under a hard wall-clock budget after which it exits 0 silently, gated behind `MLVIEW_HOOK=off`. **Landed 2026-09-10 (Sprint 5 wave 1) — measurement note.** `claude-plugin/hooks/hooks.json` wires `PostToolUse` on `Edit|Write|NotebookEdit` to `post_edit.py` and `Stop` to `stop_summary.py`, sharing `hook_core.py`; normative in `docs/CONTRACTS.md` §11.41, which amends §5 (no new tool) and §9. ## (f) Risks and open questions for the user to decide

### Decisions required before Sprint 3 starts

1. **Grant the A6 baseline amendment?** `docs/CONTRACTS.md` §10 A6 lists *"baseline"* among the *"do NOT build"* trims. That was a correct prototype scope decision and is now the measured blocker to adoption: 111 pre-existing findings on a 50-file repo means `--fail-on high` exits 2 forever. **Recommendation: grant exactly this one**, and keep refusing the other three A6 challengers — fuzzy search (substring is enough), a third LOD tier (obviated by VIEW-01), and implementing `followCursor` (delete the inert setting instead, which is the contract-compliant move).
2. **Batch the `Diagnostic.kind` enum extension?** Five proposals independently want a new value and the enum is **closed at 7**. Adding them one at a time means five amendments, five mirrored edits per §11.16, five gate passes, and an old validator rejecting each. **Recommendation: one amendment, all five values at once** — `untagged_dataflow`, `single_file_analysis`, `unresolved_callee`, `config_unresolved`, `notebook_analyzed` — or this becomes a recurring tax.
3. **Accept a third analyzer copy for PACKAGING?** The VSIX cannot work without one, and the vendor-sync gate is red right now. **Recommendation: yes, conditional on HEALTH-01 landing first and `tools/verify.py` growing a `vsix: synced core` row in the same change.**
4. **How much precision are we willing to spend?** ANA-7/8/9, DATAFLOW-IP and H5 all trade precision for recall, and one high-severity false positive costs more trust than ten misses. **Recommendation: ANA-12 is the referee and must exist before any of them merge**, with a stated numeric tolerance — suggested: zero `forbidden` findings, ever; recall may only ratchet up.
5. **Is notebook analysis in scope?** §5 non-goal 3 says explicitly that this version does not do it and that the omission is called out in the README rather than discovered by a user. NB is a deliberate scope extension, and it is L because R2.1's location guarantee breaks click-to-code in all three hosts simultaneously if the cell offsets are wrong.
6. **Does `Issue.fix` justify lifting non-goal 5?** MLV-P10's suppression subset is explicitly *inside* the non-goal and delivers most of the lightbulb value. H5 is the riskiest item on the board because it is the one that edits someone's training loop.

### Open questions the audits could not settle

- **What is an acceptable recall number?** 26% is the measured baseline. Nobody has said what "good" is, and without a target ANA-12's ratchet has a floor but no ceiling to aim at.
- **Which persona is primary?** The four questions in `REQUIREMENTS.md` §1 are a reviewer's (P2). The rail serves them; the diagram mostly does not. If P2 is primary, MLV-P1 and CI-ADOPT outrank most of the viewer work; if P3 (learning an unfamiliar repo) is primary, VIEW-01 and VIEW-10 come first. This roadmap hedges by putting the S-effort viewer *honesty* work in NOW and the M-effort *geometry* work in NEXT.
- **Should `WRAPPER_FACTOR` 0.4 stay?** It is doing exactly what it was designed to do, and the consequence is that two whole framework projects publish **zero** diagnostics. ANA-7 replaces the suppressed rules with framework-appropriate ones; until then, the honest alternative is to say so in the panel rather than show an empty list.
- **Is `MIN_ZOOM` 0.15 the right floor?** It is what makes the 360-node first paint unreadable rather than absent. VIEW-01 should make the question moot; if it does not, the floor is a product decision, not a rendering one.

### The framing to carry forward

Four independent audits, working from four angles, each discovered the same failure mode and none of them named it as one: **MLView cannot distinguish "I checked and it is fine" from "I could not check."** It appears as MLV101 silent on a function parameter with no diagnostic; as 3 of 7 findings on a single file with no caveat; as a Lightning file reporting *"not detected: objective"* while `F.cross_entropy` sits in `training_step`; as an odd-syntax file dropping an entire training step with `dynamic=0` on every node; as a notebook returning exit 4 and a green status bar. COVERAGE and ANA-5a are the first two instances of the general fix, which is why both are ranked above their individual value.

**Make "state what you could not analyze" a standing acceptance criterion for every analyzer proposal this round and next.** It is worth more to a user than any single rule, and it is what makes a 26% recall survivable while the deeper work is built. A tool that reliably tells you where it could not see is far more trustworthy than one that quietly reports zero.
